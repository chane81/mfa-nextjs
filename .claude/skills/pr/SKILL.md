# PR 작성

## 이 스킬이 푸는 문제

PR 본문을 쓰다 보면 **작업하며 알게 된 것을 전부 적게 된다.** 배경, 시도했다 만 것,
왜 그 방법이 아닌지… 쓰는 사람에게는 전부 중요했으니까.

그런데 리뷰어는 그 맥락이 없다. 긴 본문을 만나면 **읽지 않고 diff 로 내려간다.**
그러면 본문에 쓴 노력이 통째로 버려진다.

그래서 본문의 목적을 다시 잡는다. **설명하는 글이 아니라, 리뷰어를 diff 의 올바른
자리로 데려가는 안내판이다.** 배경과 근거는 버리는 게 아니라 **접어서** 필요한 사람만
펴 보게 한다.

## 절차

1. **상태 파악** — `git status`, `git log --oneline <base>..HEAD`, `git diff <base>...HEAD --stat`
2. **검증** — 저장소의 검사를 **실제로 돌린다**. 통과 못 하면 PR 을 만들지 말고 먼저 보고한다
3. **푸시** — 기본 브랜치면 먼저 브랜치를 딴다. `git push -u origin <branch>`
4. **본문 작성** — 아래 규칙대로. 파일로 쓰고 `--body-file` 로 넘긴다(따옴표 이스케이프 지옥을 피한다)
5. **생성** — `gh pr create --base <base> --head <branch> --title … --body-file …`
6. **인라인 코멘트** — 변경이 크면(대략 파일 15개 이상) 아래 "인라인 코멘트" 절을 따른다

검증 명령은 **저장소에서 찾아 쓴다.** `package.json` 의 `scripts`, `Makefile`, CI 워크플로를
보고 그 저장소가 실제로 쓰는 것을 돌린다 — 흔히 test · typecheck · lint · format 검사,
그리고 빌드가 계약을 검증하는 저장소라면 빌드까지.

제목·본문 언어는 **그 저장소의 기존 PR·커밋을 따른다**(`gh pr list`, `git log`).

## 본문 규칙

### 뼈대

```markdown
<한두 줄 요약. 이 PR 이 무엇을 바꾸는가 + 동작 변경 여부>

## 한눈에

| 무엇 | before | after |
| ---- | ------ | ----- |

<선택: 숫자 한 줄 — 줄 수, 파일 수, 삭제한 중복 개수>

---

## 1. <변경 하나>

## 2. <변경 둘>

...

## 검증

<details><summary>접어둘 것들</summary> … </details>
```

### 각 부분을 왜 그렇게 쓰나

**첫 두 줄** — 리뷰어가 가장 먼저 알고 싶은 건 "이거 위험한가" 다.
`동작 변경 없음` 인지 `사용자에게 보이는 변경` 인지를 여기서 밝힌다.

**`한눈에` 표** — before/after 는 문장보다 표가 빠르다. 3~5행이 적당하다.
6행이 넘으면 변경을 너무 잘게 쪼갠 것이니 묶는다.

**번호 섹션** — 변경 하나당 하나. **각 2~4줄.** 넘어가면 그건 접을 내용이 섞인 것이다.
섹션 안에서 정말 중요한 문장 하나는 인용문(`>`)으로 띄운다.

**코드·diff 블록** — 한 줄이 핵심이면 그 줄을 보여주는 게 설명보다 짧다.

````markdown
```diff
- const REACT_VERSION = '19.2.8';
+ const REACT_VERSION = (MODULES.react as { version: string }).version;
```
````

**`검증`** — 산문 말고 블록으로. 무엇을 돌렸고 무엇이 통과했는지만.

### 접는 기준 (`<details>`)

| 성격                        | 어디에     |
| --------------------------- | ---------- |
| 무엇이 바뀌었나             | 본문       |
| 왜 그게 문제였나 (한 문장)  | 본문       |
| 왜 다른 방법을 안 골랐나    | **접는다** |
| 만들었다 되돌린 것          | **접는다** |
| 작업 중 밟은 함정·실패 로그 | **접는다** |
| 일부러 안 고친 것과 그 이유 | **접는다** |

접는 건 **버리는 게 아니다.** 나중에 "왜 이렇게 했지" 로 이 PR 을 찾아올 사람에게는
그게 본문보다 값지다. 다만 지금 리뷰하는 사람의 첫 스크롤을 차지하면 안 될 뿐이다.

`<summary>` 는 내용을 말한다 — `자세히` 말고 `배포 예외를 만들었다가 되돌린 이야기`.

### 피할 것

- **중첩 설명** — "A 인데 그 이유는 B 이고 B 는 C 때문인데…". 한 문장에 인과는 하나.
- **같은 말 두 번** — 표에 쓴 걸 아래 문장에서 또 풀지 않는다.
- **커밋 목록 나열** — `gh` 가 이미 보여준다. 읽는 순서가 필요하면 그것만 적는다.
- **성과 자랑** — "깔끔해졌다", "훨씬 나아졌다". 숫자로 말하거나 말하지 않는다.
- **전문용어 벽** — 그 저장소 사람이라면 아는 말만 쓴다. 설명이 필요하면 접는다.

## 인라인 코멘트

변경이 크면 본문만으로는 **어느 줄이 중요한지** 전할 수 없다. 그때 `Files changed` 에
코멘트를 단다.

기준은 하나다. **diff 만 봐서는 왜 그랬는지 안 보이는 자리에만 단다.**
기계적인 치환(import 경로 재작성, 포맷 변경)에는 달지 않는다. 10~15개면 충분하다.

한 번의 리뷰로 묶어 보낸다:

```bash
gh api repos/<owner>/<repo>/pulls/<n>/reviews --method POST --input review.json
```

```json
{
  "body": "리뷰어용 메모 + 읽는 순서 제안",
  "event": "COMMENT",
  "comments": [{ "path": "src/x.ts", "line": 42, "side": "RIGHT", "body": "…" }]
}
```

⚠️ `line` 은 **diff 에 실제로 포함된** 새 파일 쪽 줄 번호여야 한다. 아니면 API 가 통째로
거절한다. 보내기 전에 확인한다:

```bash
git diff <base>...HEAD -U0 -- <path> | grep '^@@'
```

`@@ -12,3 +15,8 @@` 는 새 파일 기준 15~22줄이 코멘트 가능하다는 뜻이다.

## 이미 열린 PR 을 고칠 때

`gh pr view <n> --json body --jq .body` 로 지금 본문을 읽고, 위 규칙으로 다시 쓴 뒤
`gh pr edit <n> --body-file <파일>`. 새 PR 을 만들지 않는다.

"장황하다 / 어렵다" 는 요청이면 대개 **분량 문제가 아니라 배치 문제**다. 내용을 지우기
전에 먼저 접어 보고, 그래도 첫 화면이 안 잡히면 그때 줄인다.

## 예시

`references/example.md` 에 실제 PR 본문 하나가 통째로 들어 있다 — 69개 파일짜리 리팩터링을
어떻게 배치했는지, 무엇을 접었는지 보려면 그 파일을 읽는다. 처음 쓰는 형태가 감이 안 잡히면
거기서 뼈대만 가져다 쓴다.
