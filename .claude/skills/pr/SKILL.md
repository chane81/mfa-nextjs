# PR 작성

## 본문은 리뷰를 받기 위한 것이다

PR 본문의 성패는 길이가 아니다. **리뷰어가 읽고 나서 어디를 봐야 할지 알게 됐는가** 다.

이걸 놓치면 본문이 두 방향으로 망가진다. 하나는 작업 과정을 전부 적는 것 —
쓴 사람에게는 전부 중요했지만 리뷰어에게는 소음이다. 다른 하나는 그냥 짧게 줄이는 것 —
읽기는 쉬운데 **어디를 볼지는 여전히 모른다.**

둘 다 결과가 같다. 리뷰어가 본문을 건너뛰고 diff 를 위에서부터 훑는다. 그러면 기계적인
33개 파일에 시간을 쓰고 정작 판단이 들어간 한 파일을 대충 본다.

**본문이 할 일은 리뷰어의 시선을 배분하는 것이다.**

## 리뷰어에게 줘야 하는 것 셋

쓰기 전에 이 셋의 답부터 정한다. 답이 본문의 뼈대가 된다.

**① 어디를 봐야 하나**
판단이 들어간 자리와 기계적인 자리를 **갈라준다.** "41개 파일 중 실제로 볼 것은 셋" 이
리뷰어에게 가장 값진 한 줄이다. 큰 변경일수록 그렇다.

그리고 기계적인 쪽은 **모양을 한 번만 보여준다.** 두 줄이면 된다.

```diff
- moment(order.createdAt).format('YYYY-MM-DD HH:mm')
+ formatDate(order.createdAt, 'dateTime')
```

리뷰어는 이걸 보고 나머지 32곳을 **패턴으로** 확인한다 — 한 줄씩 읽지 않는다.
"moment 호출을 formatDate 로 바꿨습니다" 라는 **문장은 같은 일을 못 한다.**
읽고 나서도 실제 모양을 모르니 결국 diff 를 열어봐야 한다.

이게 ① 을 가장 싸게 하는 장치다. 치환·이관·이름 변경처럼 같은 변형이 반복되는
PR 이면 거의 항상 쓴다.

**② 무엇이 위험한가**
동작이 바뀌는 곳, 되돌리기 어려운 곳, 배포 순서가 걸린 곳. 리뷰어가 가장 먼저 알고
싶은 게 이거다 — 첫 두 줄에서 `동작 변경 없음` 인지 아닌지를 밝힌다.

**③ 무엇을 확인해 달라는가**
내가 확신 없는 것, 다른 판단이 가능한 것. 이걸 적으면 리뷰가 **구체적으로 돌아온다.**
없으면 "LGTM" 만 온다. 확신 없는 게 정말 없으면 안 적어도 된다 — 지어내지 않는다.

이 셋이 안 들어간 본문은 짧아도 실패다. 반대로 이 셋이 또렷하면 조금 길어도 괜찮다.

## 셋을 산문에 담지 않는다

리뷰어는 본문을 **읽지 않고 훑는다.** 표·인용·불릿·코드는 훑는 눈에 걸리지만,
같은 내용을 문장으로 풀면 **읽어야만 알 수 있는 것**이 된다. 그래서 줄을 줄이는 것보다
**산문을 형태로 바꾸는 것**이 먼저다.

같은 PR 을 두 벌로 써서 붙여본 실측이다. 짧은 쪽이 더 안 읽혔다.

| 본문                  | 첫 화면 | **산문 줄** | 구조 줄(표·인용·불릿·코드) |
| --------------------- | ------- | ----------- | -------------------------- |
| 형태로 쓴 것          | 95줄    | **16**      | 42                         |
| 줄여서 산문에 담은 것 | 81줄    | **29**      | 27                         |

총 길이를 14줄 줄이면서 **읽어야 하는 양은 두 배로 늘렸다.** 줄 수만 세면 이걸 못 본다.

무엇을 어떤 형태로 쓰나:

| 형태           | 담는 것                                                          |
| -------------- | ---------------------------------------------------------------- |
| `> 인용`       | 그 섹션에서 **가장 위험한 한 문장** — ② 는 상단에 한 번이 아니다 |
| 섹션 안 표     | 평행하게 열거되는 것 — `잊으면 / 무슨 일이`, `선택 / 틀렸을 때`  |
| 불릿           | 같은 층위의 제약 2~4개. 항목마다 이유를 한 줄로 붙인다           |
| ` ```diff `    | 기계적 치환의 **모양** (바뀐 줄만)                               |
| ` ```ts `      | 바뀐 **뒤의 호출 모양** — 불변식을 산문보다 싸게 보여줄 때       |
| `---`          | 도입부 · 섹션 묶음 · 검증 사이의 경계                            |
| ` ```mermaid ` | **배선·흐름이 바뀔 때만.** 노드 5~6개까지 (GitHub 이 렌더한다)   |

**눈에 보이는 쪽이 언제나 낫다.** 같은 사실을 리뷰어가 표에서 3초에 얻는다면 문장으로
쓸 이유가 없다. 표를 넣을지 말지 고민되면 넣는 쪽이다.

**평행한 것을 이어붙인 문장은 거의 항상 표다.** "A 를 잊으면 X 가 되고, B 를 잊으면
Y 가 된다" 는 2행 표로 쓴다 — 같은 정보인데 눈이 한 번에 잡는다.

**한 섹션에 산문 문단이 셋을 넘으면** 그중 하나는 형태로 바뀔 것이 섞여 있다.

## 그래서 장황한 설명을 걷어낸다

위 셋을 눈에 띄게 하려면 **나머지가 자리를 비켜줘야 한다.** 줄이는 건 목적이 아니라
그 수단이다 — 배경 설명 사이에 파묻힌 "여기를 보세요" 는 없는 것과 같다.

| 걷어낸다                            | 이미 어디 있나   |
| ----------------------------------- | ---------------- |
| 변경 파일 목록                      | Files changed 탭 |
| 커밋 해시·메시지 나열               | Commits 탭       |
| diff 가 보여주는 것을 문장으로 옮김 | diff             |
| 표에 쓴 것을 섹션에서 다시 풀기     | 바로 위의 표     |
| 작업한 시간 순서 · 시도한 과정      | 아무도 안 묻는다 |
| 잘 아는 라이브러리·개념 설명        | 리뷰어가 안다    |

**표는 "무엇", 섹션은 "왜".** 표에서 `메모리 Map → Redis` 를 읽은 사람에게
"저장소를 Redis 로 옮겼습니다" 라고 다시 말하지 않는다.

**섹션은 커밋 단위가 아니라 "리뷰어가 따로 판단해야 하는 것" 단위다.** 커밋이 5개여도
판단이 3개면 섹션은 3개다.

## 분량 — 지킬 선이 아니라 되돌아볼 신호

**맞춰야 하는 숫자가 아니다.** 넘겼다고 실패가 아니고, 지켰다고 성공도 아니다.
판단할 것이 넷이면 넷을 쓴다. 그 넷이 각각 또렷하면 길어도 된다.

넘겼을 때 하는 일은 깎는 게 아니라 **다시 보는 것**이다 — 핵심이 설명에 파묻혔나,
아니면 그냥 내용이 많은 것인가. 앞이면 형태를 바꾸고, 뒤면 그대로 둔다.
**숫자를 맞추려고 표를 문장으로 되돌리는 건 언제나 틀렸다.**

**다 쓰고 나서 센다.**

| 무엇                                | 선                                 |
| ----------------------------------- | ---------------------------------- |
| **첫 화면의 산문 줄**(details 제외) | **20줄 안팎**에서 한 번 되돌아본다 |
| 첫 화면 전체                        | 안 센다 — 표·코드는 스캔된다       |
| 번호 섹션                           | 3~4개                              |
| 산문 문단 하나                      | 3줄. 넘으면 표·인용으로 쪼갠다     |
| `한눈에` 표                         | 3~4행                              |
| 섹션 안 표                          | 2~4행. 칸마다 한 어절~한 줄        |
| 코드·diff 블록                      | 6줄. 하나면 더 좋다                |
| `<details>`                         | 3~4개. **안쪽은 길이를 안 센다**   |

세는 건 **산문 줄**이다. 표를 넣어 전체가 길어진 건 실패가 아니고, 표를 문장으로 풀어
전체가 짧아진 게 실패다.

산문이 넘쳤으면 줄이기 전에 먼저 묻는다 — **이 문단이 리뷰어의 판단을 돕나?**
돕는다면 형태를 바꾸고, 아니면 위 표에서 걷어낼 것을 찾는다.

진짜 기준은 하나뿐이다. **핵심이 눈에 들어오나.** 같은 말을 돌려 하고 있거나 배경이
결론 앞을 막고 있으면 20줄이 안 돼도 실패고, 판단 넷이 각각 또렷하면 30줄이어도 된다.

숫자를 세는 것보다 중요한 건 **한 섹션 = 판단 하나** 다. 섹션이 길어졌다면 대개
판단 둘이 섞였거나 접을 배경이 붙은 것이다 — 줄을 깎기 전에 그것부터 본다.

## 무엇을 접나

`<details>` 는 **창고가 아니라 각주다.** 접기 전에 먼저 묻는다 —
**이걸 버려도 되나?** 대부분 버려도 된다.

버릴 게 아니라면 **줄여서 접지 않는다.** 접힌 블록은 첫 화면 비용이 0 이라,
길이를 깎는 대신 안쪽도 표·인용으로 쓴다. 되돌린 판단의 `선택 / 틀렸을 때` 같은 표는
리뷰어가 그 결정을 다시 볼 때 쓰는 자료다 — 문장으로 뭉개면 접은 의미가 없다.
대신 **접는 개수**는 늘리지 않는다.

| 성격                       | 어디에                  |
| -------------------------- | ----------------------- |
| 무엇이 바뀌었나            | 본문                    |
| 왜 그게 문제였나 (한 문장) | 본문                    |
| 왜 다른 방법을 안 골랐나   | 접는다                  |
| 만들었다 되돌린 것         | 접는다 (표 유지)        |
| 밟은 함정·실패 로그        | 접는다 (에러 원문 유지) |
| 그 밖의 배경               | **버린다**              |

리뷰어가 물어볼 게 뻔한 것만 접는다. `<summary>` 는 내용을 말한다 —
`자세히` 말고 `dayjs 를 검토했다가 뺀 이유`.

## 뼈대

```markdown
<한두 줄. 무엇을 바꾸는가 + 동작 변경 여부> ← ②

## 한눈에

| 무엇 | before | after |

<변경이 크면: 어디를 봐야 하는지 한 줄> ← ①

## 1. <리뷰어가 따로 판단해야 하는 것 하나>

<한두 문단>

> <이 섹션에서 가장 위험한 한 문장> ← ②

<열거되는 결과가 있으면 2~4행 표>

## 2. …

## 확인 부탁 ← ③ (있을 때만)

## 검증

<details><summary>구체적인 라벨</summary> … </details>
```

**어디를 봐야 하는지**는 파일이 많을 때 한 줄이면 충분하다.

> 41개 중 판단이 들어간 건 `DateRangePicker.tsx` 하나다. 나머지는 같은 모양의 치환이다.

**확인 부탁**은 짧게, 구체적으로. "봐주세요" 말고 "이게 맞는 트레이드오프인가" 로.

> fail-open 을 골랐다. 한도가 잠깐 안 걸리는 것과 결제가 막히는 것 중 후자가 더
> 비싸다고 봤는데, 보안 쪽 판단이 다르면 알려달라.

**코드·diff 블록**은 둘 중 하나다.

- `diff` — **바뀐 줄만.** 컨텍스트 줄도, 함수 전체도 아니다. 기계적 치환의 모양을
  한 번 보여줄 때 쓴다
- `ts` 등 — **바뀐 뒤의 호출 모양.** "두 번들러 config 가 같은 객체를 받는다" 같은
  불변식은 3줄 코드가 문장보다 싸다

20줄 diff 를 붙이는 건 diff 탭을 본문에 복사하는 것이고, 그러면 리뷰어는 본문에서도
diff 에서도 같은 것을 두 번 읽는다.

**`검증`** — 산문 말고 블록으로. 무엇을 돌렸고 무엇이 통과했는지만.

## 절차

1. **상태 파악** — `git status`, `git log --oneline <base>..HEAD`, `git diff <base>...HEAD --stat`
2. **검증** — 저장소의 검사를 **실제로 돌린다**. 통과 못 하면 PR 을 만들지 말고 먼저 보고한다
3. **푸시** — 기본 브랜치면 먼저 브랜치를 딴다. `git push -u origin <branch>`
4. **본문 작성** — 위 셋을 먼저 정하고 쓴다. 파일로 쓰고 `--body-file` 로 넘긴다
5. **생성** — `gh pr create --base <base> --head <branch> --title … --body-file …`
6. **인라인 코멘트** — 변경이 크면(대략 파일 15개 이상) 아래 절을 따른다

검증 명령은 **저장소에서 찾아 쓴다** — `package.json` 의 `scripts`, `Makefile`, CI 워크플로.
제목·본문 언어는 **그 저장소의 기존 PR·커밋을 따른다**(`gh pr list`, `git log`).

## 이미 열린 PR 을 고칠 때

`gh pr view <n> --json body --jq .body` 로 지금 본문을 읽고 다시 쓴 뒤
`gh pr edit <n> --body-file <파일>`. 새 PR 을 만들지 않는다.

**"장황하다" 는 요청의 진짜 뜻은 "무엇을 봐야 할지 모르겠다" 다.** 문단을 `<details>` 로
옮기기만 하면 총량도 그대로고 요청도 안 풀린다. 원문에서 **위 셋에 해당하는 문장을 먼저
찾아 올리고**, 나머지를 걷어낸다. 원문 문단마다 갈 곳을 만들어주고 있다면 방향이 틀렸다.

**이미 형태가 잡힌 본문을 산문으로 압축하지 않는다.** 표·인용이 붙어 있는 본문에
"줄이라" 는 말이 오면 걷어낼 것은 문단이지 표가 아니다. 표를 문장으로 되돌리면
줄 수는 줄고 읽어야 하는 양은 늘어난다 — 요청과 반대 방향이다.

## 인라인 코멘트

본문의 ①("어디를 봐야 하나")을 줄 단위로 하는 것이다. 변경이 크면 본문 한 줄로는 부족하다.

기준은 하나다. **diff 만 봐서는 왜 그랬는지 안 보이는 자리에만 단다.**
기계적인 치환(import 경로 재작성, 포맷 변경)에는 달지 않는다 — 대표 한 곳에
"나머지 32개도 같은 모양" 이라고 적는 게 낫다. 10개 안팎이면 충분하다.

한 번의 리뷰로 묶어 보낸다:

```bash
gh api repos/<owner>/<repo>/pulls/<n>/reviews --method POST --input review.json
```

```json
{
  "body": "리뷰어용 메모 + 읽는 순서 제안",
  "event": "COMMENT",
  "comments": [{ "path": "src/x.ts", "line": 42, "side": "RIGHT", "body": "…" }]
}
```

⚠️ `line` 은 **diff 에 실제로 포함된** 새 파일 쪽 줄 번호여야 한다. 아니면 API 가 통째로
거절한다. 보내기 전에 확인한다:

```bash
git diff <base>...HEAD -U0 -- <path> | grep '^@@'
```
