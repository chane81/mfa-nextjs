# PR 작성

## 이 스킬이 푸는 문제

PR 본문을 쓰다 보면 **작업하며 알게 된 것을 전부 적게 된다.** 쓰는 사람에게는 전부
중요했으니까. 그런데 리뷰어는 그 맥락이 없다. 긴 본문을 만나면 **읽지 않고 diff 로
내려간다.** 그러면 본문에 쓴 노력이 통째로 버려진다.

그래서 본문의 목적을 다시 잡는다. **설명하는 글이 아니라, 리뷰어를 diff 의 올바른
자리로 데려가는 안내판이다.**

안내판은 짧아야 안내판이다. 아래 예산이 이 스킬의 전부라고 봐도 된다.

## 예산

| 무엇                           | 상한                    |
| ------------------------------ | ----------------------- |
| **첫 화면**(details 접힌 상태) | **50줄** — 스크롤 한 번 |
| 번호 섹션                      | 3~4개                   |
| 섹션 하나 (산문)               | 2~4줄 — 코드·표는 별도  |
| `한눈에` 표                    | 3~4행                   |
| 코드·diff 블록                 | 6줄. 하나면 더 좋다     |
| `<details>`                    | 3개, 하나당 5줄         |

**다 쓰고 나서 센다.** 눈대중하지 말고 실제로 센다 — 접힌 상태 줄 수, 섹션 수,
details 수. 넘으면 아래 "무엇을 버리나" 로 돌아간다.

예산이 빡빡하게 느껴진다면 맞다. 리뷰어가 본문에 쓰는 시간이 딱 그만큼이다.

## 무엇을 버리나

들어갈 것을 고르기 전에 **안 들어갈 것부터** 정한다. 이게 어려운 쪽이다.

| 버린다                              | 이미 어디 있나   |
| ----------------------------------- | ---------------- |
| 변경 파일 목록                      | Files changed 탭 |
| 커밋 해시·메시지 나열               | Commits 탭       |
| diff 가 보여주는 것을 문장으로 옮김 | diff             |
| 표에 쓴 것을 섹션에서 다시 풀기     | 바로 위의 표     |
| 작업한 시간 순서 · 시도한 과정      | 아무도 안 묻는다 |
| 잘 아는 라이브러리·개념 설명        | 리뷰어가 안다    |

**표는 "무엇", 섹션은 "왜".** 표에서 `메모리 Map → Redis` 를 읽은 사람에게
"저장소를 Redis 로 옮겼습니다" 라고 다시 말하지 않는다. 섹션은 표가 못 말하는
것 — 왜 그게 문제였고 무엇을 포기했는지 — 만 맡는다.

**섹션은 커밋 단위가 아니라 "리뷰어가 따로 이해해야 하는 것" 단위다.** 커밋이 5개여도
리뷰어가 알아야 할 판단이 3개면 섹션은 3개다.

## 무엇을 접나

`<details>` 는 **창고가 아니라 각주다.** 접을 때도 줄여서 접는다.

접기 전에 먼저 묻는다 — **이걸 버려도 되나?** 대부분 버려도 된다.
접는 건 **리뷰어가 물어볼 게 뻔한 것**에만 쓴다.

| 성격                       | 어디에           |
| -------------------------- | ---------------- |
| 무엇이 바뀌었나            | 본문             |
| 왜 그게 문제였나 (한 문장) | 본문             |
| 왜 다른 방법을 안 골랐나   | 접는다 (3~5줄로) |
| 만들었다 되돌린 것         | 접는다 (3~5줄로) |
| 밟은 함정·실패 로그        | 접는다 (3~5줄로) |
| 그 밖의 배경               | **버린다**       |

`<summary>` 는 내용을 말한다 — `자세히` 말고 `dayjs 를 검토했다가 뺀 이유`.

## 뼈대

```markdown
<한두 줄. 무엇을 바꾸는가 + 동작 변경 여부>

## 한눈에

| 무엇 | before | after |

<선택: 숫자 한 줄 — 파일 수, 줄 수, 번들 크기>

## 1. <리뷰어가 알아야 할 판단 하나>

## 2. …

## 검증

<details><summary>구체적인 라벨</summary> … </details>
```

**첫 두 줄** — 리뷰어가 가장 먼저 알고 싶은 건 "이거 위험한가" 다.
`동작 변경 없음` 인지 `사용자에게 보이는 변경 있음` 인지를 여기서 밝힌다.

**코드·diff 블록** — 한 줄이 핵심이면 **그 한 줄만** 보여준다. 20줄 diff 를 붙이는 건
diff 탭을 본문에 복사하는 것이다.

````markdown
```diff
- const REACT_VERSION = '19.2.8';
+ const REACT_VERSION = (MODULES.react as { version: string }).version;
```
````

**`검증`** — 산문 말고 블록으로. 무엇을 돌렸고 무엇이 통과했는지만.

## 절차

1. **상태 파악** — `git status`, `git log --oneline <base>..HEAD`, `git diff <base>...HEAD --stat`
2. **검증** — 저장소의 검사를 **실제로 돌린다**. 통과 못 하면 PR 을 만들지 말고 먼저 보고한다
3. **푸시** — 기본 브랜치면 먼저 브랜치를 딴다. `git push -u origin <branch>`
4. **본문 작성** — 위 예산대로. 파일로 쓰고 `--body-file` 로 넘긴다
5. **생성** — `gh pr create --base <base> --head <branch> --title … --body-file …`
6. **인라인 코멘트** — 변경이 크면(대략 파일 15개 이상) 아래 절을 따른다

검증 명령은 **저장소에서 찾아 쓴다** — `package.json` 의 `scripts`, `Makefile`, CI 워크플로.
제목·본문 언어는 **그 저장소의 기존 PR·커밋을 따른다**(`gh pr list`, `git log`).

## 이미 열린 PR 을 고칠 때

`gh pr view <n> --json body --jq .body` 로 지금 본문을 읽고 다시 쓴 뒤
`gh pr edit <n> --body-file <파일>`. 새 PR 을 만들지 않는다.

**"장황하다" 는 요청은 분량이 목표다.** 원문의 절반 이하를 노린다. 문단을 `<details>`
로 옮기기만 하면 총량은 그대로고 요청은 안 풀린다 — 옮기기 전에 **버릴 것부터** 고른다.
원문 문단마다 갈 곳을 만들어주고 있다면 방향이 틀렸다.

## 인라인 코멘트

변경이 크면 본문만으로는 **어느 줄이 중요한지** 전할 수 없다. 그때 `Files changed` 에
코멘트를 단다.

기준은 하나다. **diff 만 봐서는 왜 그랬는지 안 보이는 자리에만 단다.**
기계적인 치환(import 경로 재작성, 포맷 변경)에는 달지 않는다. 10개 안팎이면 충분하다.

한 번의 리뷰로 묶어 보낸다:

```bash
gh api repos/<owner>/<repo>/pulls/<n>/reviews --method POST --input review.json
```

```json
{
  "body": "리뷰어용 메모 + 읽는 순서 제안",
  "event": "COMMENT",
  "comments": [{ "path": "src/x.ts", "line": 42, "side": "RIGHT", "body": "…" }]
}
```

⚠️ `line` 은 **diff 에 실제로 포함된** 새 파일 쪽 줄 번호여야 한다. 아니면 API 가 통째로
거절한다. 보내기 전에 확인한다:

```bash
git diff <base>...HEAD -U0 -- <path> | grep '^@@'
```

`@@ -12,3 +15,8 @@` 는 새 파일 기준 15~22줄이 코멘트 가능하다는 뜻이다.

## 예시

`references/example.md` 에 예산을 지킨 본문 하나(접힌 상태 47줄 · 섹션 3개)가 있다.
형태가 감이 안 잡히면 읽는다. 그 파일은 **무엇이 버려졌는지**를 입력과 대조해 보여준다 —
넣을 것을 고르는 것보다 그쪽이 어렵다.
