`evals/fixtures/01-rate-limit.md` 를 입력으로 만든 것이다.

## 셋이 어디에 들어갔나

| 무엇                   | 이 본문에서                                                |
| ---------------------- | ---------------------------------------------------------- |
| **② 무엇이 위험한가**  | 첫 두 줄 — `동작 변경 있음` 과 그 내용                     |
| **① 어디를 봐야 하나** | 섹션 제목이 곧 판단 셋이다 + 미들웨어 변화를 3줄 diff 로   |

③ 이 이 본문에서 가장 값진 한 문단이다. 이게 없으면 `LGTM` 만 오고, 정작 뒤집을 수도

IP 당 요청 한도를 프로세스 메모리에서 Redis 토큰 버킷으로 옮긴다.
**동작 변경 있음** — 인스턴스 수와 무관하게 한도가 걸리고(지금까지 2대 = 실효 2배), 429 에 `retry-after` 가 붙는다.

## 한눈에

| 무엇          | before                | after                   |
| ------------- | --------------------- | ----------------------- |
| 카운터 저장소 | 프로세스 메모리 `Map` | Redis (Lua 원자 연산)   |
| 실효 한도     | 인스턴스 수 × `MAX`   | `MAX` 하나              |
| 429 응답      | 본문만                | `retry-after` 헤더 추가 |
| 한도 판정     | 미들웨어 안           | `src/limiter/bucket.ts` |

8 파일 · +331 / -88

## 1. 인스턴스를 늘린 순간 한도가 조용히 2배가 됐다

카운터가 프로세스 메모리에 있었다. 2대로 늘린 뒤 실효 한도도 같이 2배가 됐다.

> **429 가 안 나가니 아무 신호가 없었다.** 한도가 풀린 걸 알 방법이 로그에도 대시보드에도 없다.

미들웨어는 이제 판정을 위임만 한다.

```diff
-  const held = counters.get(key);
-  if (!held || held.resetAt < now) { … }
+  const verdict = await takeToken(req.ip);
```

## 2. `INCR` + `EXPIRE` 두 번 호출은 영구 차단을 만든다

두 명령 사이에서 프로세스가 죽으면 키가 **TTL 없이** 남는다. 그 IP 는 창이 영영 안 열린다. 그래서 조회·보충·기록을 Lua 하나로 합쳤다. `EVALSHA` 로 캐시하고 `NOSCRIPT` 면 한 번만 다시 올린다.

## 3. Redis 가 죽으면 통과시킨다 (fail-open)

한도를 셀 수 없는 동안은 막지 않는다. 결제 API 라 **오차단이 초과 허용보다 비싸다.**

| 선택        | Redis 가 죽었을 때    |
| ----------- | --------------------- |
| fail-open   | 한도가 잠깐 안 걸린다 |
| fail-closed | 결제가 통째로 막힌다  |

반대로 가려면 이 판단부터 뒤집어야 한다.

`retry-after` 도 같이 넣었다 — 없을 때 클라이언트가 즉시 재시도해서 부하가 오히려 늘었다.

설정 셋 추가: `RATE_LIMIT_REDIS_URL` · `RATE_LIMIT_MAX`(100) · `RATE_LIMIT_WINDOW_SEC`(60)

## 확인 부탁

fail-open 을 골랐다. 한도가 잠깐 안 걸리는 것과 결제가 막히는 것 중 후자가 더 비싸다고 봤는데, 보안 쪽 판단이 다르면 알려달라.
