## 개요

이 PR 은 우리 파이프라인의 적재 단계에서 발생하던 중복 레코드 문제를 해결하기 위한 것입니다. 먼저 배경을 설명드리자면, 우리 파이프라인은 매일 새벽 3시에 외부 벤더의 S3 버킷에서 파일을 가져와서 스테이징 테이블에 적재한 뒤, 거기서 다시 dbt 를 통해 마트 테이블로 변환하는 구조로 되어 있습니다. 그런데 지난달부터 마트 테이블의 일부 레코드가 중복되는 현상이 보고되었고, 데이터 팀에서 확인 요청이 들어왔습니다. 처음에는 dbt 모델의 조인 조건에 문제가 있는 것으로 의심했지만, 스테이징 테이블을 직접 조회해 보니 이미 그 단계에서 중복이 존재하고 있었습니다. 그래서 적재 단계를 다시 살펴보게 되었습니다.

적재 단계를 살펴보니 벤더가 같은 파일을 두 번 올리는 경우가 있었습니다. 벤더 쪽에 문의한 결과 그들의 배치가 실패하면 재시도를 하는데 그 과정에서 이미 성공적으로 업로드된 파일도 다시 올린다는 답변을 받았습니다. 파일 이름에는 타임스탬프가 붙어 있어서 우리 쪽에서는 서로 다른 파일로 인식하고 두 번 적재하게 됩니다. 벤더에게 수정을 요청했지만 그들의 로드맵상 3분기 이후에나 가능하다고 하여 우리 쪽에서 방어하기로 했습니다.

그래서 이 PR 에서는 파일의 내용 해시를 계산해서 이미 적재한 해시면 건너뛰는 방식을 도입했습니다. 해시는 SHA-256 을 사용하고 `ingested_files` 라는 새 테이블에 기록합니다. 이 테이블에는 해시, 파일명, 적재 시각, 레코드 수를 저장합니다. 처음에는 파일명만으로 중복을 판단하려고 했으나 위에서 설명한 대로 타임스탬프가 달라서 불가능했고, 파일 크기로 판단하는 방법도 고려했지만 크기가 같은 다른 파일이 존재할 수 있어서 위험하다고 판단했습니다. 내용 해시가 가장 확실한 방법입니다.

해시 계산 비용에 대해서도 검토했습니다. 파일이 평균 200MB 정도이고 하루 40개 정도가 들어오는데, 전체를 읽어서 해시를 계산하면 8GB 를 읽게 됩니다. 하지만 어차피 적재를 위해 전체를 읽어야 하므로 추가 비용은 해시 계산 자체의 CPU 비용뿐이고, 실측 결과 파일당 1.2초 정도가 추가되어 전체 40개 기준 48초가 늘어납니다. 현재 파이프라인 전체가 40분 정도 걸리므로 2% 증가이고 허용 가능한 수준으로 판단했습니다. 스트리밍으로 읽으면서 해시를 갱신하기 때문에 메모리 사용량은 늘지 않습니다.

또한 이번 기회에 적재 실패 시의 동작도 정리했습니다. 기존에는 적재 도중 실패하면 이미 들어간 레코드가 남아 있어서 재실행하면 그 부분이 중복되었습니다. 이제는 트랜잭션으로 묶어서 실패하면 전부 롤백되도록 했고, `ingested_files` 기록도 같은 트랜잭션 안에서 이루어지므로 해시가 기록되었다는 것은 적재가 완료되었다는 것을 의미합니다. 다만 파일이 매우 큰 경우 트랜잭션이 길어지는 문제가 있어서 배치 크기를 5만 행으로 나누고 배치마다 커밋하는 방식도 검토했으나, 그러면 부분 적재 상태가 다시 생기므로 채택하지 않았습니다. 대신 워크 메모리를 늘리는 것으로 대응했습니다.

테스트는 단위 테스트 12개와 통합 테스트 3개를 추가했습니다. 단위 테스트는 해시 계산, 중복 판단, 트랜잭션 롤백을 각각 검증하고 통합 테스트는 실제 Postgres 컨테이너를 띄워서 같은 파일을 두 번 적재했을 때 두 번째가 건너뛰어지는지, 적재 도중 예외가 발생했을 때 롤백되는지, 그리고 서로 다른 파일 두 개가 정상적으로 모두 적재되는지를 확인합니다. 기존 테스트는 모두 통과하며 커버리지는 78%에서 84%로 올랐습니다.

마이그레이션이 하나 포함되어 있습니다. `ingested_files` 테이블을 생성하는 것이고 기존 데이터에는 영향이 없습니다. 다만 배포 후 첫 실행에서는 기록이 비어 있으므로 그날 들어온 파일은 모두 적재됩니다. 이는 의도된 동작이며 그 전에 이미 적재된 중복은 이 PR 로 제거되지 않으므로 데이터 팀에서 별도로 정리 쿼리를 실행해야 합니다. 정리 쿼리는 이 PR 에 포함하지 않았고 별도 티켓 DATA-1188 로 관리합니다.

배포 순서는 마이그레이션을 먼저 적용하고 그 다음에 애플리케이션을 배포하면 됩니다. 롤백이 필요한 경우 애플리케이션만 이전 버전으로 되돌리면 되고 테이블은 남아 있어도 무해합니다.
