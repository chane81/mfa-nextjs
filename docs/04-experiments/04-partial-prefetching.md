# 실험 — 부분 프리페칭(Partial Prefetching)

`next@16.3.1` · `partialPrefetching: true` · **검증일: 2026-08-23**

측정 환경: macOS, 프로덕션 빌드(`pnpm start`), 헤드리스 Chrome, remote 는 `serve-remote-dist`
가 서빙하는 빌드 산출물. 같은 머신에서 baseline → 플래그 on 순으로 연달아 쟀다.

## 한 줄

**전송량은 25~45% 줄었고 요청 건수는 그대로였다.** 그리고 그 이유가 이 저장소의 구조를
드러냈다 — 부분 프리페칭이 노리는 이득의 본체를 **우리는 애초에 못 받는다.**

## 먼저, 이름이 비슷한 다른 것과 구분

| 이름                           | 무엇                                            | 빌드 표기               |
| ------------------------------ | ----------------------------------------------- | ----------------------- |
| Partial Pre**render**ing (PPR) | **서버**가 HTML 을 만드는 방식 (정적 셸 + 구멍) | `◐ (Partial Prerender)` |
| Partial Pre**fetch**ing        | **브라우저**가 `<Link>` 로 미리 받는 것         | 빌드 표에 안 나타난다   |

`cacheComponents` 를 켜면 앞의 것이 켜지고, 뒤의 것은 **별도 플래그**다.
그리고 뒤의 것은 앞의 것이 켜져 있어야만 동작한다.

## 무엇이 달라지는가

프리페치 단위가 **링크마다 → 라우트마다**로 바뀐다.

- 전: `<Link href="/products/1">` 이 자기 목적지의 렌더를 받아온다. 링크 100개 = 프리페치 100번
- 후: Next 가 `/products/[id]` **라우트당 App Shell 하나**를 만들고 그 라우트로 가는
  모든 링크가 그걸 공유한다

App Shell = **정적 콘텐츠 + URL 에 의존하지 않는 캐시된 콘텐츠.** 판정 기준은 하나다 —
"이 값이 **URL 마다** 달라지나?"

| 읽는 것                   | URL 데이터 | App Shell |
| ------------------------- | ---------- | --------- |
| `params` · `searchParams` | ⭕         | ❌        |
| `cookies()` · `headers()` | ❌         | ⭕        |

`cookies()` 가 셸에 들어가는 게 직관에 어긋나 보이지만 근거가 분명하다 — 그건 **세션마다**
다르지 **링크마다** 다르지 않다. 한 사용자에게는 어느 링크를 눌러도 같은 값이다.

`<Link prefetch={true}>` 의 뜻도 바뀐다. "동적 콘텐츠까지 다" → "App Shell + **URL 에
의존하는** 콘텐츠까지". URL 과 무관한 동적 콘텐츠는 이제 안 딸려온다.

## 측정 방법

```bash
git checkout -b experiment/partial-prefetching   # main 에서
# apps/host/next.config.ts 에 partialPrefetching: true 추가
pnpm start                                        # 프리페치는 프로덕션에서만 돈다
```

브라우저(헤드리스)로 페이지를 열고 networkidle 까지 기다린 뒤 끝까지 스크롤해서
뷰포트 밖 `<Link>` 까지 프리페치시킨다. 그다음 페이지 안에서 Resource Timing 을 읽는다.

```js
performance
  .getEntriesByType('resource')
  .filter((e) => e.name.includes('_rsc=') || e.name.includes('.rsc'))
  .map((e) => ({
    url: e.name,
    enc: e.encodedBodySize,
    dec: e.decodedBodySize,
  }));
```

> ⚠️ **`curl` 로 프리페치를 흉내내지 말 것.** `RSC: 1` + `Next-Router-Prefetch: 1` 만 보내면
> `◐` 라우트가 **404** 를 준다(`next-router-state-tree` 가 빠져서다). 버그가 아니라 합성
> 요청이 불완전한 것이고, 그걸 모르면 없는 장애를 쫓게 된다.
> `vary` 가 실제 축을 알려준다:
> `rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch`.
> 브라우저가 실제로 보낸 것을 재는 편이 언제나 맞다.

## 결과

### 전송량 — 일관되게 줄었다

| 방문 페이지        | 요청 건수 | 전송(enc)                    | 해제(dec)                    |
| ------------------ | --------- | ---------------------------- | ---------------------------- |
| `/`                | 8 → 8     | 8,177 → 6,070 B (**−26%**)   | 20,818 → 13,093 B (**−37%**) |
| `/lab`             | 15 → 15   | 14,506 → 10,151 B (**−30%**) | 36,228 → 20,057 B (**−45%**) |
| `/products/kb-001` | 10 → 10   | 10,343 → 7,708 B (**−25%**)  | 25,880 → 15,916 B (**−39%**) |

목적지별로 보면 감소가 고르지 않다 — 캐시 가능한 몫이 클수록 많이 준다.

| 목적지     | baseline(enc) | ppf(enc) |      |
| ---------- | ------------- | -------- | ---- |
| `/lab/isr` | 2,177         | 949      | −56% |
| `/debug`   | 1,597         | 974      | −39% |
| `/cart`    | 1,561         | 1,096    | −30% |
| `/lab`     | 2,611         | 2,070    | −21% |

목적지마다 요청이 **두 건**인 건 양쪽 다 같다(작은 것 ~210B + 본체). 부분 프리페칭이
바꾸는 건 본체 크기지 요청 횟수가 아니다 — 적어도 이 저장소에서는.

### 라우트 표 — 완전히 동일

`/`·`/cart`·`/checkout` = `ƒ`, `/lab` 계열 = `◐`. 당연하다. 프리페칭은 빌드 산출물이
아니라 런타임 동작이다. **빌드 표만 보고는 이 플래그가 켜졌는지조차 알 수 없다.**

### 깨진 것 없음

- ADR-014 유지 — 서로 다른 쿠키 A·B 로 `/`·`/cart`·`/checkout` 을 요청해 첫 HTML 에
  각자의 합계가 들어가고 쿠키가 없으면 빈 장바구니. 교차 오염 없음
- 프리페치 응답에 **어느 세션의 장바구니도 들어있지 않다** — 셸에 세션 콘텐츠가 새지 않는다
- 클릭 내비게이션 정상 — 홈에서 "장바구니" 클릭 → `/cart`, 배지·패널 합계 모두 정확,
  에러 박스 0, 남은 스켈레톤 0, 콘솔 에러 0
- `/lab/isr` 프리렌더 HTML 에 remote 마크업 2 + 상품 카드 8

> 검증 중 `/` 에서 "B 세션 응답에 A 의 값(189,000원)이 있다"가 한 번 참으로 나왔다.
> **오염이 아니라 테스트 결함이다** — `kb-001` 상품 가격이 189,000원이라 홈 그리드에는
> 장바구니와 무관하게 늘 찍힌다. 판별자는 그 라우트에서 **장바구니에만** 나타나는 값으로
> 골라야 한다.

## 왜 요청 건수가 안 줄었나 — 이게 진짜 발견이다

부분 프리페칭의 간판 이득은 "같은 라우트로 가는 링크 N 개 → 셸 1개 공유"다.
**우리는 그 패턴이 하나도 없다.**

이 저장소의 `<Link>` 는 전부 다섯 개고 전부 서로 다른 라우트를 가리킨다.

```
SiteHeader.tsx      / · /cart · /checkout · /debug · /lab   (헤더 네비 5개)
lab/page.tsx        /lab/ssr · /lab/isr · /lab/cache        (실험 인덱스 3개)
products/[id]       /                                        (뒤로 가기 1개)
```

N:1 패턴이 나올 유일한 자리는 **상품 목록 → `/products/[id]`** 인데, 거기는 `<Link>` 가
아니다.

```tsx
// apps/remote-catalog/src/components/ProductCard.tsx — 링크가 아니라 버튼이다
<button onClick={() => onSelect?.(product)}>{product.name}</button>;

// apps/host/src/components/CatalogSection.tsx — host 가 라우팅을 소유한다
onSelect: (product) => router.push(`/products/${product.id}`);
```

**이건 설계상 그렇게 된 것이다.** remote 는 host 의 라우터를 몰라야 하므로(ADR-013,
`docs/02-architecture/03-ssr-and-soft-nav.md`) 상세 이동을 콜백으로 위임한다. 그 대가로
그 자리는 `<Link>` 가 아니게 되고, **프리페치가 아예 일어나지 않는다** — 실측에서 `/` 를
열었을 때 프리페치 목적지에 `/products/*` 가 **한 건도 없다.**

즉 이 저장소에서 부분 프리페칭의 이득은 "헤더 네비 링크 다섯 개의 페이로드가 얇아진 것"
뿐이다. 간판 이득은 구조적으로 못 받는다.

### 그래서 남는 질문 — MFA 에서 remote 가 그리는 목록은 프리페치를 포기하나

일반적인 트레이드오프다. remote 가 라우팅을 모르게 하려면 콜백이고, 콜백이면 `<a>` 가
아니고, `<a>` 가 아니면 프리페치도 없고 새 탭 열기·링크 복사도 없다.

풀 방향은 있다 — host 가 `onSelect` 대신 **링크를 렌더하는 함수**를 props 로 내려보내면
(`renderLink?: (href, children) => ReactNode`) remote 는 여전히 라우터를 모른 채
host 의 `<Link>` 를 쓸 수 있다. 계약이 하나 늘어나는 값을 하는지는 별도 판단이라
여기서는 기록만 한다.

## 결론 — 지금은 켜지 않는다

- 얻는 것: 헤더 네비 프리페치 −25~45%. 절대량으로는 페이지당 2~4KB(enc)
- 잃는 것: 없음(측정 범위 내). 깨진 동작 0
- **안 켜는 이유**: 이 저장소의 산출물은 성능이 아니라 **기록**이고, 이 플래그가 바꾸는
  건 이 저장소가 검증하려는 주장(런타임 MF + remote SSR)과 무관하다. 설정을 하나 늘리면
  나중에 MF 관련 증상을 볼 때 배제해야 할 변수가 하나 는다.
- **켤 만한 조건**: `<Link>` 로 같은 라우트를 여러 번 가리키는 화면이 생기면. 위의
  `renderLink` 를 도입해 상품 카드가 진짜 링크가 되는 순간이 정확히 그 시점이다.

측정 브랜치: `experiment/partial-prefetching` (머지하지 않는다).
