# CI (`ci.yml`)

정적 검사 · 테스트 · 빌드를 **세 job 으로 나눠** 돌린다. 셋은 서로 의존하지 않아 동시에 뜬다.

| job      | 무엇                                          | 대략 |
| -------- | --------------------------------------------- | ---- |
| `verify` | lint · lint:docker · typecheck · format:check | 짧다 |
| `test`   | vitest 단위 · 통합                            | 중간 |
| `build`  | remote → host, 프리렌더가 SSR 실행            | 길다 |

이 파일은 워크플로의 **근거**를 담는다. `ci.yml` 자체에는 각 단계가 무엇을 하는지만 한 줄씩 둔다.

## 왜 `build` 가 CI 에 있나

host 의 `next build` 는 순수 컴파일이 아니다. 프리렌더가 remote 의 SSR 번들을 HTTP 로 받아
**실제로 실행해본다**(`apps/host/src/mf/loader/server.ts`). 그래서 빌드가 통과한다는 건
"Next 16 에서 런타임 MF + SSR 이 된다"는 이 저장소의 유일한 주장이 아직 참이라는 뜻이다.
빌드를 빼면 그 주장이 깨져도 PR 이 초록으로 통과한다.

remote → host 순서와 빌드 중 dist 서빙은 turbo 와 host 의 build 스크립트가 처리한다.
띄울 remote 는 `REMOTE_LIST` 가 정하므로 **remote 가 늘어도 `ci.yml` 은 안 바뀐다.**
배경: [01-getting-started.md](./01-getting-started.md) 의 "host 빌드는 remote 가 떠 있어야 끝난다".

## 왜 세 job 인가

피드백 속도와 **실패 원인의 분리**다. 붙여두면 빠른 신호가 느린 신호를 기다리고, 무엇보다
체크 이름만 보고는 "포맷이 틀렸나 테스트가 깨졌나"를 구분할 수 없다.

`test` job 이 `build` 에 얹히지 않는 이유는 따로 있다 — 테스트가 워크스페이스 패키지의 `src` 를
alias 로 직접 가리켜서 **빌드 없이 돈다**. 목록과 배경:
[06-testing/01-test-plan.md](../06-testing/01-test-plan.md).

`pnpm test` 는 일부러 turbo 를 타지 않는다. 패키지별 대응 태스크가 없어 얻는 게 캐시뿐인데,
그 대가로 `--project=dom` 같은 러너 플래그가 turbo 에 먹힌다.

## 왜 이미지 빌드가 여기 없나

한때 있었다(38차). 39차에 뺐다 — **아무것도 막지 못했기 때문이다.** `deploy` 워크플로에
`needs: ci` 도 `workflow_run` 도 없고 main 에 브랜치 보호도 없어서 두 워크플로가 같은 push 에
나란히 뜬다. CI 가 빨개도 배포는 그대로 나갔다. 게다가 `push: false` 라 만든 이미지를 버리고
Dokploy 가 같은 Dockerfile 로 다시 빌드했다.

이미지가 깨지면 `dokploy-deploy` 가 `deployment.all` 의 status 로 잡는다(근거: ADR-023).
Dockerfile 의 워크스페이스 목록 드리프트(known-issues I-10)는 `scripts/docker-context.test.ts` 가
`pnpm test` 에서 잡는다.

## `permissions: contents: read`

이 저장소는 공개다. fork 가 연 PR 도 여기서 `pnpm build` 를 돌린다 — 그 워크플로가 받는
`GITHUB_TOKEN` 이 무엇을 할 수 있는지 기본값에 맡기지 않는다. CI 는 코드를 읽기만 하면 된다.
쓰기 권한은 `mf-revalidate` 쪽에도 필요 없다(시크릿만 쓴다).

## 각 단계가 거기 있는 이유

| 단계                          | 근거                                                                                                                                        |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `node -v && pnpm -v`          | `pnpm install` 은 `pnpm/setup` 이 이미 돌렸다. `engineStrict: true` 라 Node 가 범위 밖이면 여기서 `ERR_PNPM_UNSUPPORTED_ENGINE` 으로 죽는다 |
| `actions/cache` (Tailwind)    | 디자인 시스템 캐시가 비면 `pnpm lint` 가 0.6s → 3.8s 다. 키와 측정: [ADR-028 보강](../02-architecture/01-decision.md)                       |
| `pnpm lint`                   | oxlint 가 저장소 전체(테스트 · scripts 포함)를 한 번에 돈다                                                                                 |
| `pnpm lint:docker`            | Dockerfile 을 `docker build --check` 로 본다. 빌드는 하지 않는다 — 러너에 docker 가 있다                                                    |
| `pnpm typecheck`              | turbo 로 패키지 태스크 + 루트 태스크(`typecheck:scripts` · `typecheck:tests`)를 함께 돈다                                                   |
| `pnpm format:check`           | oxfmt. Dockerfile 은 포매터를 두지 않는다(ADR-028 보강)                                                                                     |
| 세 job 모두 `pnpm/setup` 캐시 | 같은 lockfile · 같은 Node 범위라 캐시 키를 공유한다                                                                                         |

## MF DTS 가 최신인지 확인하는 단계

`packages/contracts/src/generated/` 는 생성물인데도 커밋한다 — `remote-contract.ts` 가 그 타입과
목록을 실제로 쓰기 때문이다. 안 그러면 `pnpm typecheck` 가 remote 기동을 요구하게 되고, 그건 이
저장소가 DTS 를 오래 껐던 바로 그 이유다.

대가는 **낡을 수 있다는 것**이고, 그걸 이 단계가 잡는다. remote 의 props 를 고치고
`pnpm mf:types` 를 안 돌리면 host 는 옛 타입으로 통과한다 — `typecheck` 는 커밋된 파일만 보므로
그 어긋남을 못 본다.

바로 앞 `pnpm build` 가 remote dist 를 이미 만들어 뒀으므로 정적 서버만 띄우면 된다.
`serve-all-remotes` 가 `REMOTE_LIST` 를 순회해 전부 띄우고 페치가 끝나면 같이 내린다 —
여기도 remote 를 추가해도 안 바뀐다.
