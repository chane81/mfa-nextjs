mfa-nextjs · 쉬운 판

웹사이트 하나를
세 팀이 따로 배포하는 법

손님에게는 사이트 하나로 보이는데, 만드는 쪽에서는 앱 셋이 각자 배포된다. 이 저장소는 그게 Next.js 16 에서 되는지를 확인한 실험 기록이다. 이 문서는 코드를 모르는 사람도 순서를 따라갈 수 있게 푸드코트 하나로 끝까지 설명한다.

host 건물 전체 · Next.js 16 · :3000 catalog 입점 가게 ① · Vite 8 · :3001 cart 입점 가게 ② · Rsbuild 2 · :3002
정확한 판은 따로 있다. 용어를 이미 아는 사람은 Next 16 페더레이션 해부도 를 보면 된다. 같은 구조를 레인·분기까지 그린 문서다. 색(파랑 host · 보라 catalog · 초록 cart)은 두 문서가 같다.
01

먼저 그림 한 장 — 이게 전부다

비유

푸드코트를 떠올리면 된다. 건물은 하나다. 출입구도 하나, 복도도 하나, 안내판도 하나. 그런데 안에 들어가 있는 가게는 각자 다른 회사다. 손님은 그걸 눈치채지 못한다 — 쟁반 하나 들고 돌아다니면 음식이 담길 뿐이다.

진짜 이름

건물 = host. 가게 = remote. 가게가 내놓는 메뉴 = expose 한 모듈. 이 구조 전체를 마이크로 프론트엔드(Micro Frontend) 라고 부르고, 가게 코드를 건물이 실행 시점에 받아오는 방식을 Module Federation 이라고 한다.

02

왜 굳이 나누나 — 한 덩어리일 때 생기는 일

비유

식당 한 곳이 메뉴 전부를 만든다고 해보자. 김밥 단무지를 바꾸려고 해도 가게 문을 닫았다가 다시 열어야 한다. 그동안 파스타도 못 판다.

푸드코트면 단무지 바꾸는 가게만 셔터를 내린다. 옆 가게도 건물도 그냥 영업한다.

진짜 이름

가게마다 셔터를 따로 내리는 것 = 독립 배포. 이 저장소는 앱 셋을 각자 컨테이너 이미지로 올린다(ADR-009). 배포 순서는 사람이 아니라 CI 가 쥐고, 가게(remote) 를 먼저 열고 건물(host) 을 나중에 연다 — 이유는 다음 절에 나온다.

03

어려운 부분은 여기다 — 손님이 오기 전에 접시를 채워야 한다

비유

보통의 푸드코트라면 손님이 가게 앞에 가서 주문하면 된다. 그런데 이 건물의 규칙은 다르다 — 손님이 문을 열고 들어오는 순간 이미 쟁반에 음식이 담겨 있어야 한다. 빈 접시를 들려주고 "곧 나옵니다" 하면 안 된다.

그래서 건물이 손님보다 먼저 움직인다. 가게에 전화해서 조리법을 통째로 받아와, 건물 주방에서, 건물 식기로 직접 만든다.

같은 화면인데 손님이 이미 들어온 뒤에 필요해질 수도 있다. 그때는 건물이 아니라 브라우저가 직접 가게에 전화한다. 받아오는 파일이 다를 뿐(서버용 mf-server.cjs ↔ 브라우저용 remoteEntry.js) 규칙은 같다 — 식기는 언제나 건물 것이다.

진짜 이름

손님 오기 전에 접시를 채우는 것 = SSR(서버 사이드 렌더링). 그래서 remote 는 같은 소스에서 두 벌로 빌드된다 — 브라우저용 remoteEntry.js + mf-manifest.json, 서버용 mf-server.cjs.

건물 식기를 쥐여주는 것 = React 인스턴스 주입. 서버 쪽은 new Function 으로 평가하면서 require 를 가로채고, 브라우저 쪽은 Module Federation 의 shared 선언이 같은 일을 한다(ADR-005).

음식은 오는데 그릇 색은 안 온다. 가게의 CSS 는 이 두 경로 어디로도 따라오지 않는다. 그래서 host 가 가게를 꽂는 자리에서 그 가게의 스타일 주소를 <link> 로 같이 건다 — 같은 주소는 React 가 알아서 하나로 합친다(ADR-011).

그리고 이게 가게를 먼저 배포하는 이유다 — host 는 빌드할 때도 가게 코드를 실제로 받아 실행해 본다. 가게가 안 떠 있으면 host 빌드가 거기서 멈춘다. 즉 빌드가 통과했다는 사실 자체가 이 저장소의 주장에 대한 증거다.

04

가게를 옮겨 다녀도 건물 밖으로 나가지 않는다

비유

상품을 보다가 결제하러 갈 때, 손님이 건물 밖으로 나갔다가 옆 건물로 다시 들어가야 한다면? 들고 있던 쟁반을 입구에 두고 나가는 셈이다. 화면은 하얗게 한 번 번쩍이고, 스크롤 위치도 장바구니도 다시 그려진다.

이 저장소는 결제 코너까지 같은 건물 안에 넣었다. 손님은 복도를 걸어갈 뿐이다.

진짜 이름

복도를 걸어가는 것 = 소프트 내비게이션. 길을 건너는 것 = 하드 내비게이션(문서를 새로 받는다). Multi-Zones 는 건물마다 라우터가 따로라 경계를 넘을 때 하드 내비게이션이 강제된다 — 그래서 라우터는 host 하나만 두는 쪽을 택했다.

가게는 복도 구조를 아예 모른다. "다 됐으니 홈으로 보내 달라"를 건물에 부탁할 뿐이다 — remote 는 라우터를 모르고, 이동은 host 가 넘겨준 콜백으로 위임한다 (onDone: () => router.push('/')).

05

가게가 새 단장을 하면 건물은 어떻게 아나

비유

가게가 메뉴를 바꾸면 정문에 걸린 메뉴판 한 장을 갈아 끼운다. 건물은 30초에 한 번 그 메뉴판만 흘깃 본다. 가게가 건물에 전화를 걸어 알리기도 하지만, 그건 빨리 알리려는 것일 뿐이다 — 전화가 끊겨도 30초 뒤면 어차피 맞춰진다.

지난 메뉴는 창고에 최근 다섯 개까지 남긴다. 이미 인쇄되어 나간 전단(캐시된 화면)이 옛 번호를 가리키고 있기 때문이다 — 창고를 비우면 그 손님 화면이 깨진다.

진짜 이름

메뉴판 = mf-version.json(버전 공표, TTL 30초). 창고 선반 = 불변 경로 /v<version>/. 전화 = POST /api/mf-revalidate 웹훅 — 유실돼도 TTL 로 수렴하므로 정합성 문제가 아니다. 데운 뒤 버리는 순서 = warm-then-revalidate. 캐시는 네 층이고 무효화 태그도 층마다 따로다(ADR-007) — 전부 04-remote-lifecycle.md.

06

남이 만든 코드를 우리 서버에서 돌린다 — 검문 네 겹

비유

03 절을 다시 보자. 건물 주방에서 가게가 보낸 조리법을 그대로 실행한다. 조리법이 바꿔치기당하면 건물 주방이 통째로 넘어간다.

그래서 배달을 받을 때 네 번 확인한다. 뒤로 갈수록 강하고, 앞의 것이 없으면 뒤의 것도 의미가 없다.

진짜 이름

① 오리진 허용 목록 — 기본값이 이미 닫혀 있고 REMOTE_ALLOWED_ORIGINS 로만 넓힌다. ② 경로 형태 검증. ③ SRI 해시 대조(SHA-384). ④ Ed25519 서명 검증 — 개인키는 remote 의 빌드 파이프라인이, 공개키는 host 가 가진다. 구현은 apps/host/src/mf/trust/, 브라우저 번들에도 섞이므로 node:crypto 가 아니라 WebCrypto 를 쓴다.

실제로 변조해 보고 확인했다 — 번들 바이트 변조 · 매니페스트가 외부 오리진 지정 · 경로 탈출 · 서명 없이 매니페스트 교체 · 서명은 둔 채 해시만 교체, 다섯 가지 모두 502 로 거부하면서 서비스는 계속 떴다(04-remote-lifecycle.md).

07

가게 둘을 일부러 다른 장비로 지었다

비유

한 가게는 A 사 주방 설비로, 다른 가게는 B 사 설비로 지었다. 일부러 그랬다 — "이 건물은 특정 설비 회사에 묶이지 않는다" 를 보여야 하니까. 건물이 요구하는 건 설비가 아니라 콘센트 규격뿐이다.

진짜 이름

콘센트 규격 = Module Federation. catalog 는 @module-federation/vite, cart 는 @module-federation/rsbuild-plugin. 그리고 host 는 번들러 플러그인을 아예 쓰지 않는다 — @module-federation/runtime 만 쓴다. Next 16 의 Turbopack 은 Module Federation 을 몰라도 된다는 뜻이고, 이 저장소가 성립하는 이유이기도 하다.

둘 다 되지만 편하기는 다르다. 규격이 도구 밖에 있는 Vite 쪽은 개발 서버가 차가울 때 순서가 어긋나는 문제가 있어 따로 손을 봐야 했고, 서버용 번들을 만드는 설정도 더 길다. 한 줄 결론 — MF remote 전용으로 새로 짓는다면 Rsbuild. 그래도 catalog 를 옮기지 않는 건 두 번들러가 공존하는 것 자체가 이 실험이기 때문이다 (04-bundler-comparison.md).

08

가게끼리는 말을 걸지 않는다 — 그럼 장바구니는?

비유

상품 코너에서 "담기"를 누르면 장바구니 숫자가 올라간다. 두 코너는 다른 가게인데 어떻게 아나? 가게끼리 전화하는 게 아니다 — 쟁반은 가게 것이 아니라 손님 것이고, 그 쟁반을 건물이 관리한다.

가게끼리 직접 연결하면 한 가게가 옆 가게 영업시간에 묶인다. 그래서 규칙이 하나다 — 가게는 건물하고만 대화한다.

그리고 한 가게에 불이 나면

건물을 닫지 않는다. 그 코너만 에러 상자로 바뀌고 나머지 화면은 그대로 뜬다. 응답 자체는 정상(200)이라 손님은 상품도 보고 결제도 할 수 있다 — 못 쓰는 건 고장 난 코너 하나뿐이다.

진짜 이름

보관함 = @mfa/store. 어느 쪽이 먼저 로드되든 같은 것을 보도록 globalThis 에 싱글턴으로 잡고(ADR-004 · ADR-012), 저장소는 쿠키다 — 서버가 읽을 수 있어야 첫 HTML 부터 개수가 맞기 때문이다(ADR-014).

공유하는 것은 상태이지 코드가 아니다. 그래서 @mfa/store 와 @mfa/ui 는 Module Federation 의 shared 에 올리지 않는다 — 올리면 버전 협상이 붙어 한 remote 의 배포가 다른 remote 의 런타임을 바꾼다 (ADR-022). 대가는 remote 수에 비례하는 중복(현재 remote 당 gzip 수 KB)이고, 그걸 받아들인 것이다.

에러 상자 = RemoteBoundary (apps/host/src/mf/components/). 그리고 remote → remote 의존을 금지하는 이 규칙이 02-topology.md 의 "remote 는 host 하고만 대화한다"다.

10

그래서 이 저장소가 증명한 것

한 문단 요약

Next.js 16 에서 공식 플러그인이 죽은 뒤에도 런타임 Module Federation 이 된다. 가게 코드는 host 서버에서 실행되어 SSR 된 HTML 로 나가고, 손님은 경계를 넘어도 화면이 끊기지 않는다. 가게는 혼자 배포되고, 되돌리기는 파일 한 장이며, 그 코드를 실행하기 전에 네 번 검문한다.

증거는 문장이 아니라 빌드다 — pnpm build 가 통과하면 host 프리렌더가 실제로 remote 의 서버 번들을 받아 실행했다는 뜻이다. 그래서 이 저장소는 빌드 실패를 우회하지 않는다.
