번들러 플러그인 없이 @module-federation/runtime 만으로 remote 를 SSR 하고, 경계를 넘어도 소프트 내비게이션을 유지한다. 배포는 앱 셋이 각자, 런타임은 host 하나가 합친다. 이 문서는 그 두 축을 그림으로 설명한다.

PART 1

배포 — 저장소는 하나, 배포 단위는 셋

근거 문서 03-setup/04-dokploy.md 02-architecture/04-remote-lifecycle.md 03-setup/03-environment.md 04-experiments/03-cache-modes.md

마이크로 프론트엔드의 값어치는 독립 배포 하나로 결정된다. 그래서 세 앱을 한 Compose 로 묶지 않고 각각 별도의 Application 으로 올린다 — catalog 만 고쳐서 배포했을 때 host 가 무중단인지가 이 구조가 증명하려는 것이다.

1-1. 푸시 하나에서 배포 셋이 갈라진다

함정 — 왜 host 이미지는 build 가 아니라 docker:build 를 부르나

로컬 build 는 워크스페이스 remote 를 먼저 빌드해서 띄운다. 그런데 이미지 안에서 remote 는 이미 배포된 공개 도메인이다. 같은 태스크 이름을 쓰면 catalog 빌드 실패가 host 배포까지 끌고 내려가 빌드 그래프에서 독립 배포가 다시 묶인다. 그래서 remote 게이트만 뺀 태스크로 이름을 갈랐다.

1-2. remote 아티팩트는 불변, 볼륨에 덧붙인다

컨테이너는 휘발이다. 이미지 안의 dist 만 서빙하면 재배포 순간 이전 버전이 사라지고, 이미 캐시된 host HTML 이 가리키던 옛 청크가 hydration 단계에서 404 가 된다.

1-3. 재배포를 host 에 알리는 경로

remote 를 따로 배포하면 host 는 바뀐 사실을 알 방법이 없다 — 페이지 캐시가 옛 remote 마크업을 계속 서빙한다. Dokploy 에는 배포 후 훅이 없어서, 그 자리를 GitHub Actions 가 폴링 후 웹훅으로 메운다.

1-4. 어디까지가 빌드 시점에 굳는 값인가

값 주는 방법 런타임에 바꿀 수 있나 왜

remote 쪽 		Build Arg 불가 자산 URL 접두사(base / assetPrefix)로 청크마다 박힌다

PART 2

런타임 — host 와 remote 는 어떻게 만나나

근거 문서 02-architecture/03-ssr-and-soft-nav.md 02-architecture/02-topology.md 02-architecture/01-decision.md 02-architecture/04-remote-lifecycle.md 02-architecture/05-styling.md

요구사항은 두 개였다. remote 영역이 SSR 될 것, 그리고 경계를 넘어도 소프트 내비게이션일 것. Multi-Zones 는 두 번째에서, CSR 전용 MF 는 첫 번째에서 탈락한다.

2-1. 라우터를 하나만 둔다 — 소프트 내비게이션의 정체

2-2. 같은 호출이 실행 환경에 따라 두 갈래로 갈린다

@module-federation/nextjs-mf 는 Next 16 을 지원하지 않고, @module-federation/node 는 peer 가 webpack 이다. host 는 Turbopack 이라 webpack 이 없다. 그래서 host 에는 번들러 플러그인을 아예 넣지 않고, 런타임 라이브러리만 평범하게 쓴다.

여기서 가장 자주 걸리는 질문 — “남의 코드를 서버에서 실행한다고요?”

그렇다. 그래서 신뢰 경계를 별도로 설계했다(2-4). 브라우저에서 remote 청크를 실행하는 것과 신뢰 수준은 같지만, 뚫렸을 때 영향 범위가 서버 프로세스라는 점이 다르다는 게 판단의 출발점이었다.

2-3. remote 를 소비하는 자리는 단 하나다

모든 remote 소비가 RemoteComponent 하나를 지난다. 이 진입점이 세 가지를 한 번에 감싼다 — 서버·브라우저 두 로딩 경로, remote 하나가 죽어도 host 는 사는 장애 격리(RemoteBoundary), 그리고 remote 의 스타일시트다.

CSS 는 두 로딩 경로 어디로도 따라오지 않는다. 브라우저에서는 MF 런타임이 모듈만 가져오고, 서버에서는 CJS 문자열을 평가할 뿐이라 스타일시트를 실을 자리가 없다. 그래서 host 가 소비하는 자리에서 <link rel="stylesheet" precedence> 를 함께 건다 — React 19 가 <head> 로 올리고 같은 href 를 중복 제거하므로, 한 화면에 같은 remote 를 몇 개 놓든 링크는 하나다.

캐시 층 담는 것 무효화 수단 수명
1 · 버전 매니페스트 mf-version.json 응답 revalidateTag(…version) expire:0 TTL 30초
2 · 번들 응답 mf-server.cjs 바이트 revalidateTag(…bundle) expire:0 태그까지
3 · 평가된 모듈 new Function 결과 버전 변경 · warm 세대 증가 프로세스
4 · 페이지 remote 마크업이 든 HTML/RSC revalidateTag(…remote, "max") cacheLife

태그를 세 개로 나눈 이유가 여기 있다. 하나로 묶으면 순서를 만들 수 없다 — 번들을 깨는 순간 페이지도 같이 깨져서 재생성이 warm 보다 먼저 일어난다. 그리고 1·2 는 expire:0, 4 는 "max" 다. "max" 는 stale-while-revalidate 라 번들 계층에 쓰면 warm 이 옛 코드를 데우고 remote 가 죽어 있어도 “성공”해버린다. 반대로 페이지 계층에서는 SWR 이 맞다.

2-4. host 서버가 남의 코드를 실행하기 전에 통과시키는 네 겹

mf-version.json 은 remote 가 주는 값이다. 그대로 믿으면 “이 주소에서 이 파일을 받아 실행하라”는 지시를 그대로 따르게 된다. 그래서 실행 전에 두 가지를 확인한다 — 받은 파일이 도중에 바뀌지 않았나(내용), 그리고 이 지시를 정말 우리 remote 빌드가 냈나(출처).

③ 해시는 무엇을 대조하나 — 그리고 왜 그것만으로는 부족한가

해시는 파일 내용을 짧은 문자열로 요약한 값이다. 내용이 1바이트만 달라져도 값이 전혀 다르게 나온다. 그래서 remote 가 매니페스트에 적어 보낸 해시와, host 가 받은 파일을 직접 계산한 해시를 맞춰보면 전송 중 잘렸거나 바뀐 파일을 잡아낼 수 있다. 이 대조가 SRI 이고, 요약을 만드는 방식이 SHA-384 다.

문제는 해시를 적어 보내는 쪽과 파일을 주는 쪽이 같다는 것이다. remote 오리진이 통째로 털리면 공격자는 번들을 바꾸고 해시도 다시 계산해서 매니페스트에 써넣으면 된다. host 가 보기에 둘은 정확히 일치한다. 같은 출처가 준 값끼리 대조하는 자기 증명이라, 이 공격은 원리적으로 막히지 않는다.

④ 그래서 비대칭키를 쓴다 — 만드는 열쇠와 확인하는 열쇠를 나눈다

서명은 “이 내용을 우리가 냈다”를 증명하는 장치다. 핵심은 열쇠가 한 쌍이라는 데 있다. 한쪽(개인키)으로만 서명을 만들 수 있고, 다른 한쪽(공개키)으로는 확인만 된다. 공개키를 아무리 들여다봐도 개인키를 되돌릴 수 없고, 따라서 공개키를 가진 쪽은 가짜 서명을 만들지 못한다. 이 “한 방향으로만 되는” 성질이 비대칭키의 전부이고, Ed25519 는 그 성질을 구현한 방식 중 하나다.

그래서 배치가 결정된다. 개인키는 remote 의 빌드 파이프라인 안에만, 공개키는 host 의 런타임 env 에만 둔다. 오리진이 털려도 공격자에게는 개인키가 없으니 번들과 해시는 바꿔도 서명은 만들 수 없다. 결과적으로 “배포된 파일을 바꾸는 사고”와 “빌드 파이프라인을 뚫는 사고”가 분리된다 — 둘 다 뚫려야 host 가 속는다.

만약 양쪽이 같은 비밀 하나를 나눠 갖는 방식(대칭키)이었다면, 확인만 하면 되는 host 도 서명을 만들 수 있는 열쇠를 갖게 된다. host 가 털리는 순간 그 열쇠로 가짜 remote 를 서명할 수 있으니, 막으려던 것을 못 막는다. 확인만 하면 되는 쪽에 위조 능력을 주지 않는 것 — 비대칭을 쓰는 이유가 이것이다.

2-5. remote 끼리는 서로를 모른다 — 상태는 어떻게 공유하나

catalog 의 “담기” 버튼이 cart 의 헤더 배지를 바꾼다. 그런데 규칙은 “remote 는 host 하고만 대화한다” 다. remote 가 다른 remote 를 import 하면 독립 배포 전제가 깨지고, 한쪽이 스토어를 expose 하면 remote → remote 의존이 생긴다.

그래서 스토어를 공유 패키지(@mfa/store)에 두고 globalSingleton 으로 한 인스턴스만 살린다. 전부 host 페이지 안이라 소프트 내비게이션 중 상태가 메모리에 그대로 남는다 — 저장소는 새로고침 복원용이지 경계 통신 수단이 아니다. Multi-Zones 였다면 경계마다 그 왕복이 강제됐다.

그 저장소는 쿠키다(mfa-cart). 처음엔 localStorage 였는데, 그러면 서버가 장바구니를 모르니 첫 HTML 이 항상 비어 있고 하이드레이션 커밋에서 값이 한 프레임에 바뀐다 — 사용자에게는 깜빡임이다. 쿠키는 요청에 실려 가므로 host 가 읽어 initialLines props 로 remote 에 넘길 수 있다. 담는 것은 [{id, q}] 뿐이고 이름·가격은 카탈로그에서 복원한다. 대가는 /·/cart·/checkout 의 정적 셸이다(근거: ADR-014).

FAQ

설계를 두고 자주 나오는 질문

“그냥 Multi-Zones 를 쓰면 되지 않나”

zone 마다 Next 라우터가 따로 있어서 next/link 로 경계를 넘을 수 없다. 넘을 때마다 하드 내비게이션이 강제되는데, 그러면 SPA 를 유지할 이유가 사라진다. 대조군으로 실제 zone 앱을 두고 쟀고 document 요청이 +1 로 나왔다. 측정이 끝난 뒤 그 앱은 지웠다.

“왜 공식 플러그인을 쓰지 않나”

@module-federation/nextjs-mf 는 peer 가 Next 15 에서 끊기고 App Router 를 지원한 적이 없으며 업스트림이 maintenance mode 다. @module-federation/node 는 peer 가 webpack 인데 host 는 Turbopack 이다. 그래서 host 에는 번들러 플러그인을 넣지 않고 @module-federation/runtime 만 평범한 라이브러리로 쓴다 — Turbopack 이 MF 를 몰라도 된다.

“remote 를 재배포하면 host 는 그걸 어떻게 아나”

두 경로다. remote 가 mf-version.json 으로 자기 버전을 공표하고, host 는 그 파일을 30초 TTL 로 읽어 스스로 수렴한다. 웹훅은 그 수렴을 즉시로 당기는 최적화일 뿐이라 유실돼도 정합성이 깨지지 않는다. 다만 이미 캐시된 페이지 HTML 은 태그를 깨야만 바뀌므로, 웹훅이 warm 을 먼저 하고 성공했을 때만 페이지 태그를 무효화한다.

“host 서버에서 remote 코드를 실행하는 게 위험하지 않나”

브라우저에서 remote 청크를 실행하는 것과 신뢰 수준은 같지만, 뚫렸을 때 영향 범위가 서버 프로세스라 다르다. 그래서 실행 전에 네 가지를 확인한다 — 아는 주소에서 받았는가, 경로가 뒤틀리지 않았는가, 받은 파일의 내용이 그대로인가, 그리고 이 목록을 정말 우리 빌드가 냈는가.

앞의 세 개만으로는 부족하다. 파일 내용 대조에 쓰는 해시를 remote 가 같이 보내주기 때문에, 오리진이 털리면 공격자가 파일을 바꾸고 해시도 다시 계산해 써넣으면 그대로 통과한다. 자기가 낸 답을 자기가 채점하는 구조다.

그래서 마지막 겹에 비대칭키 서명을 쓴다. 서명을 만들 수 있는 열쇠(개인키)는 remote 의 빌드 파이프라인에만 두고, host 에는 확인만 되는 열쇠(공개키)를 둔다. 오리진을 장악해도 서명은 만들 수 없으니 거기서 걸린다. 반대로 host 와 remote 가 같은 비밀을 나눠 갖는 방식이었다면 host 가 털리는 순간 가짜 remote 를 서명할 수 있게 된다. 변조 배포 5종을 직접 시도해 전부 502 로 거부되는 것까지 확인했다.

“이 구조의 한계는 무엇인가”

remote 를 웹 · 노드 두 타깃으로 빌드해야 하고, remote 는 여전히 클라이언트 컴포넌트라 서버 컴포넌트를 federate 할 수 없다. new Function 평가가 필요해 Edge 런타임도 쓸 수 없다. 그리고 웹훅은 인스턴스 하나에만 닿으므로 멀티 인스턴스 무효화는 TTL 만큼 지연된다 — 즉시성이 필요하면 공유 캐시 핸들러를 붙여야 한다.
