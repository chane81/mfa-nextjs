mfa-nextjs · 번들러 시네마

remote 둘을 일부러 다른 번들러로 만들었다.
그래서 무엇이 갈렸나

catalog 는 Vite 8, cart 는 Rsbuild 2(Rspack). "번들러가 달라도 런타임 계약만 맞으면 host 가 똑같이 소비한다" 는 Module Federation 의 주장을 실제로 세워보기 위해서다. 검증은 통과했고 — 그 과정에서 갈린 지점이 이 저장소에서 가장 값진 기록이 됐다. 계약이 어디서 오는지, 두 번들러가 그걸 어떻게 다르게 만족시키는지, 그리고 어디서 실제로 깨졌는지를 순서대로 본다.

이 그림이 주장하는 것

  • 계약은 번들러 설정에 없다. 파일 이름 · 경로 규칙 · exposes 키 · shared 선언 · SSR external 이 전부 packages/remote-config 한 곳에서 나오고, 두 config 는 그걸 자기 문법으로 받아 적기만 한다. 그래서 host 는 어느 remote 가 어느 번들러로 만들어졌는지 모른다.
  • "된다"와 "쉽다"는 다르다. 둘 다 동작한다. 다만 밟은 함정이 Vite 5건 · Rsbuild 1건이고, Vite 쪽은 전부 MF 통합 지점의 런타임 레이스인 반면 Rsbuild 쪽 하나는 네이티브 바이너리 설치 문제였다. 원인은 도구의 품질이 아니라 shared 배리어가 런타임 안에 있느냐 어댑터가 밖에서 흉내내느냐 다.
  • 그래도 바꾸지 않는다. catalog 를 Rsbuild 로 옮기면 "번들러가 달라도 된다" 는 검증 자체가 사라진다. 새로 만드는 MF remote 라면 Rsbuild 를 고르겠다는 판단과, 이 저장소를 그대로 두겠다는 판단은 서로 모순이 아니다.
