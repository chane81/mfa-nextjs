host(Next 16) 하나와 remote(Vite · Rsbuild) 둘이 따로 빌드되고 따로 배포된다. 따로 배포되는 순간 "누가 먼저인가"가 곧 정확성이 된다 — 순서를 뒤집으면 타입 검사가 잡지 못하는 조합이 런타임에 생기고, 캐시 무효화를 먼저 하면 빈 스켈레톤이 캐시에 굳는다. 아래 세 시나리오는 그 순서를 실제 파이프라인 그대로 재생한다.

이 그림이 주장하는 것

  • 순서는 CI 가 만든다. Dokploy 에는 앱 사이의 순서 개념이 없다 — 경로가 바뀌면 각자 뜰 뿐이다. 그래서 세 앱의 Autodeploy 를 끄고 GitHub Actions 가 API 로 트리거하며 완료까지 기다린다.
  • 웹훅은 최적화지 정합성 장치가 아니다. 웹훅이 유실돼도 모든 host 인스턴스는 버전 매니페스트 TTL 30초 안에 새 remote 로 수렴한다. 웹훅은 그 수렴을 즉시로 당길 뿐이다.
  • 나쁜 배포를 거부해도 서비스는 계속 뜬다. 서명·무결성 검증에 실패하면 502 로 중단하고 페이지 캐시를 건드리지 않는다 — 사용자는 마지막 정상 화면을 계속 본다.
